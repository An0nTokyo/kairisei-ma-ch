# 统一账号存档与 Android 微型服务端

## 目标

S 用同一套账号表管理全部玩家，包括现在单独存放的 `1000001`。手机上的 Sm 是 Android 应用，在离线时为游戏提供已借出账号的单人服务。游戏只修改服务器地址。

## 决定

采用方案 1。Kotlin 负责页面和前台服务。Go 程序 `kairi-mserver` 负责账号、规则和协议。`mserver` 与 `server` 同级，单独 `go.mod`，用 `replace` 引用 `../server`。游戏规则调用现有 `server` 包，不复制。

不采用 gomobile 把服务编进界面进程，也不采用浏览器打开本机页面。

## 范围

S 的改动在现有 `server` 内。Sm 的 Go 代码在 `mserver`。Android 界面和前台服务放在 `mserver` 下的 Android 工程。

不改这些行为：

- 游戏客户端除服务器地址外不做修改。
- `1000001` 仍是合法玩家号下界。好友、密码、邮件和发号的范围判断不变。
- 登录回包里 `1000001` 的 `uid = local-cn-user`、`session = local-cn-session` 不变。`sess_key` 和 `userid` 仍用账号自己的值。
- Sm 不创建账号，不向游戏提供 CPK、补丁或图片实体。
- 好友、真人组队、运营后台、CDN 和账号注册不进入 Sm。
- 邮件编号相撞只记录，本次不处理。
- schema 3 的启动校验保留。`cn_save_snapshot` 表保留，迁移后不再读写。

## 总体结构

S 是账号的登记处和最终存放处。Sm 只借出已经存在的账号。

Android 应用在阶段 C 只配置 Sm 的本机端口。电脑上的 S 地址留到借出和交还。前台服务拉起 `kairi-mserver`，通知栏保持一条前台通知。`kairi-mserver` 监听 `0.0.0.0` 和该本机端口，战斗端口为主端口加 `1`。登录回包、资源版本和服务器列表里的主机，取客户端这次连接在本机一侧的地址。页面按网卡列出这些地址。

停止服务只结束前台服务和 Go 进程。持有者不变。下次启动继续使用应用目录里的账号库和规则主数据。

一个账号同时只有一个持有者。不是持有者的一侧拒绝该账号的请求。

## S：统一账号存档

启动时，若 `cn_save_snapshot` 有 singleton 行，且 `cn_account_snapshot` 没有 `1000001`，把 singleton 的 JSON、`revision` 和摘要抄入 `cn_account_snapshot`。卡牌、道具、礼物和余额已经按 `user_id` 存放，不搬。逐账号表里这个号已有的旧副本忽略，只以 singleton 为准。抄写后摘要必须与 singleton 一致，否则启动失败且不改持有关系。

空库不再创建 singleton。第一个账号与其他账号一样，从种子档插入 `cn_account_snapshot`。

以下路径只读写 `cn_account_snapshot`：

- 读档与写档
- 注册
- 批量事务
- 单人通关落库
- 账号投影
- 后台账号列表
- 运营清理

## 所有权与转交

S 记录账号、持有者、借出时的 `revision`、主数据摘要。应用首次启动时生成 UUID，存在应用目录，作为这台手机的持有者标识。未知 UUID 登录被拒绝，不分配新的 `user_id`。

转交开始前游戏必须已关闭。当前持有者拒绝该账号的新请求。已经进入处理的请求按断网收尾：拷贝前写完，或整段取消。然后冻结资产。

冻结期间，房间结算和发放不修改背包与货币，写入账号外的邮箱队列。所有权回到 S 并且接收事务提交之后，S 把该队列插入邮箱一次。插入使用 S 当时的邮箱编号。

转交载荷只有冻结后的账号 JSON、余额、卡牌、道具和礼物，以及主数据摘要。不含通关计次、全服配置和其他账号。Sm 上产生的通关次数和通关卡组不交回，S 上的 `cn_battle_clear_daily` 保持原样。

规则主数据在借出时从 S 取到应用目录。摘要不一致则拒绝转交。摘要覆盖 S 读档时实际加载的卡牌模板和成长表。版本号相同但文件不同，视为不一致。

接收端用一次事务写入载荷中的账号内容，并更新该账号的投影。事务失败则整笔回滚，持有者不变。事务成功后才改持有者，然后解除接收端冻结。内容摘要未变时再次写入不增加 `revision`，账号 JSON 和行数据保持不变。

交回时，S 的 `revision` 与借出记录不同则不自动覆盖。Sm 页面列出两边进度，玩家选择的一边整包覆盖。

## Sm 应用与 mserver

阶段 C 的页面只有本机端口、启动、停止、按网卡列出的地址和日志。S 的地址、借出、交回和选择保留哪一边在阶段 D。

应用目录保存账号库、规则主数据、页面配置和日志。

已实现的游戏路由调用现有 `server` 包，并先确认本机是持有者。未实现路由进入同一个降级器。降级响应是 HTTP 200，`res_code` 为 `-1`，`res_str` 为「该功能需要连接电脑上的服务器」。不写账号库，不删除游戏已下载的资源。

借出时保存的资源版本用于客户端版本检查。CPK、补丁和图片实体请求走降级器，不读盘、不转发。

## 阶段

| 阶段 | 模块 | 完成标准 |
| --- | --- | --- |
| A | S 统一账号存档与一次性迁移 | 新库和已有库的 `1000001` 都只从 `cn_account_snapshot` 加载，进度与迁移前一致 |
| B | 持有者、冻结、事务导出与导入、主数据摘要、邮箱队列 | 非持有者请求被拒绝；转交失败不留下旧背包配新关卡；通关计次不在载荷中；交回后邮箱队列只插入一次 |
| C | Android 页面、前台服务、通知栏，以及 `mserver` 的监听、登录回包和降级器 | 能启动和停止。启动后按网卡列出客户端可用地址。登录回包使用本次连接的本机地址。停止后账号仍在手机。未实现请求得到降级响应且不写档 |
| D | 借出与交回 | 游戏关闭后能取走并交回账号。摘要不一致时拒绝。`revision` 变化时由玩家选择 |
| E | 主页、养成、剧情、探索、单人副本、抽卡、商店、任务、邮箱 | 这些请求走现有规则，并写入手机上的账号库 |
| F | 本机 AI 房，以及借出时另存的只读防守卡组打竞技场 | 未挂上之前继续降级。防守卡组不属于账号事务载荷 |

A 和 B 不引用 `mserver`。C 可以在没有真实账号时启动。D 只调用 B 的导出和导入。E 按路由挂现有 handler，不改规则。F 未挂上的路由保持降级。

## 测试

沿用现有包内测试。

- A：singleton 迁移成功；逐账号表中的旧副本不当正本；摘要不符时启动失败。
- B：接收事务回滚后持有者不变；非持有者被拒绝；邮箱队列在交回后只插入一次；载荷不含通关计次。
- C：降级响应不写档；停止后本地账号仍在。登录回包主机和地址列表的测试见阶段 C 规格。
- D 与 E：借出后的单人请求写入手机库；交回后 S 读到同一份进度。
